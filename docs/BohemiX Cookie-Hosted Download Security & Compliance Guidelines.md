# BohemiX 安全合规准则：浏览器 Cookie 托管"零持久化、零上传"原则

**文档版本**：1.0
**适用范围**：所有涉及 Nexus Mods 浏览器 Cookie 提取、解密、使用及网络请求的模块
**强制级别**：**最高 (Critical)** - 违反此原则的代码将直接被拒绝合并 (Reject)，并可能触发安全审计。

## 1. 概述

在 BohemiX 的"浏览器 Cookie 托管"方案中，我们需要读取用户本地浏览器的 Nexus Mods 会话 Cookie 以实现无痛下载。由于 Cookie 本质上是用户的身份凭证，等同于账号密码，我们必须严格遵守  **"零持久化、零上传"**  原则。

本准则旨在从工程实现层面彻底杜绝凭证泄露风险，确保 BohemiX 符合 Nexus Mods 的服务条款 (ToS) 以及 GDPR 等隐私法规，维护项目声誉与用户信任。

## 2. 核心定义

- **零持久化 (Zero-Persistence)**：Cookie 数据**仅允许在程序运行时的易失性内存 (RAM) 中存在**。严禁以任何形式（明文、密文、哈希、截断）写入硬盘、数据库、注册表、配置文件或系统日志。
- **零上传 (Zero-Upload)**：Cookie 数据**仅允许作为 HTTP 请求头发送至 Nexus Mods 官方域名**。严禁通过任何网络通道（包括遥测、崩溃报告、分析工具）将 Cookie 发送至第三方服务器或 BohemiX 自身的后端。

## 3. 零持久化 (Zero-Persistence) 实施细则

### 3.1 内存生命周期管理

- **强制使用安全容器**：提取和解密后的 Cookie 必须存储在 `SecureString`（C#/.NET）或平台等效的安全内存容器中，禁止使用普通的 `String` 或 `byte[]`（因为普通字符串在 GC 回收前会在内存中残留且可能被交换到虚拟内存）。
- **阅后即焚 (Read-and-Destroy)**：Cookie 变量必须在**单次 HTTP 请求完成后立即销毁**。
    - 必须显式调用 `Dispose()` 或使用 `ZeroMemory()` 等底层 API 将内存块覆写为零。
    - 禁止依赖垃圾回收器 (GC) 自动清理。
- **禁止缓存与池化**：严禁将 Cookie 放入全局缓存、对象池或单例状态中。每次下载任务必须重新从浏览器提取并解密（或在极短的下载会话内保持内存引用，会话结束立刻销毁）。

### 3.2 日志与调试输出

- **绝对脱敏**：所有日志系统（如 Serilog, NLog, `console.log`）必须配置全局过滤器。
- **占位符替换**：如果在日志上下文中检测到疑似 Cookie 的变量名（如 `session_id`, `sid`, `cookie`），其值必须被强制替换为 `[REDACTED]` 或 `***`。
- **禁止 Dump 内存**：在 Debug 模式下，禁止使用会序列化完整内存状态的工具（如某些 Profiler）且未配置脱敏规则。

### 3.3 崩溃转储 (Crash Dumps) 与遥测

- **排除敏感内存**：如果项目集成了崩溃收集工具（如 Sentry, Bugsnag），必须在配置中明确排除包含 Cookie 变量的内存区域，或在发送前进行正则清洗。
- **禁用自动 Dump**：在发生未捕获异常时，禁止自动生成包含完整堆内存的 `.dmp` 文件，除非用户手动触发且经过明确的隐私警告。

## 4. 零上传 (Zero-Upload) 实施细则

### 4.1 网络请求白名单

- **硬编码域名校验**：在底层 HTTP 客户端（如 `HttpClient`）的请求拦截器/中间件中，必须加入强制校验逻辑：
- **禁止重定向泄露**：HTTP 客户端必须**禁用自动重定向**（`AllowAutoRedirect = false`），或确保重定向策略在跨域时自动剥离 Cookie 请求头，防止 302 跳转将 Cookie 泄露给第三方 CDN 或追踪器。

### 4.2 第三方 SDK 与依赖限制

- **隔离执行环境**：Cookie 提取与解密模块必须与包含第三方分析 SDK（如 Google Analytics, Mixpanel）的模块严格隔离。
- **禁止序列化传输**：严禁将包含 Cookie 的对象传递给任何 IPC（进程间通信）机制、WebSocket 或消息队列。

## 5. 代码审查 (Code Review) 强制检查清单

在合并任何涉及 Cookie 处理的 Pull Request 前，审查者必须逐项确认以下清单：

- **容器检查**：Cookie 是否使用了 `SecureString` 或等效的安全内存类型？
- **清理检查**：在 `finally` 块或 `using` 语句中，是否显式调用了内存清零/释放方法？
- **持久化检查**：是否搜索了 `File.Write`, `Registry.SetValue`, `SQLite`, `JSON.Serialize` 等关键字，确保没有 Cookie 变量被写入？
- **日志检查**：是否在 `Log.Information/Debug/Error` 中直接打印了 Cookie 变量？
- **网络检查**：HTTP 请求的 URL 是否硬编码或严格限制为 `*.nexusmods.com`？
- **重定向检查**：HTTP 客户端是否配置了安全的重定向策略（跨域剥离 Header）？
- **异常检查**：在 `catch` 块中，是否不小心将包含 Cookie 的 `Exception` 对象发送到了远程日志服务器？

## 6. 违规处理与应急响应

### 6.1 违规行为定级

- **P0 级 (致命)**：将 Cookie 写入磁盘、发送至非 Nexus 域名、在公开 Issue/日志中暴露明文 Cookie。
- **P1 级 (严重)**：使用普通 `String` 存储 Cookie 且未在使用后清零、崩溃转储未脱敏。

### 6.2 应急响应流程

一旦发现 P0 级违规或潜在泄露：

1. **立即阻断**：在 1 小时内发布热更新 (Hotfix)，禁用 Cookie 托管功能，强制降级为 OAuth 或手动 API Key 模式。
2. **影响评估**：排查泄露范围，确认是否有用户凭证被滥用。
3. **透明沟通**：若确认发生实质性泄露，必须在 24 小时内通过官方渠道（Discord/GitHub/官网）发布公告，指导用户在 Nexus Mods 网页端强制登出 (Invalidate Sessions) 并修改密码。
4. **复盘与追责**：进行 Root Cause 分析，更新本准则，并对相关代码引入自动化静态扫描规则 (SAST) 以防止重犯。
